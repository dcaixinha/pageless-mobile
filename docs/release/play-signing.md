# Play upload key and signed AAB process

How to produce a signed Android App Bundle for the Google Play upload, and how
the four different signing keys in this project relate to each other.

Tracked by beads issue **pm-a6l.8**.

> **Nothing in this document is a secret.** Keystores, passwords, aliases and
> their locations must never be committed to Git, pasted into beads, written into
> Gradle files that are tracked, or echoed in CI logs.

## The four keys, and which is which

Confusing these is the most common way to lose the ability to ship updates.

| Key | Who holds it | What it does | Recoverable? |
| --- | --- | --- | --- |
| **Upload key** | **You** | Signs the AAB you upload to Play. Google uses it only to verify the upload came from you | **Yes** — Google can reset it if it is lost or compromised |
| **App signing key** | **Google Play** | Signs the APKs actually delivered to users' devices | Held by Google under Play App Signing, so losing your machine does not lose it |
| **F-Droid key** | **F-Droid** | Signs the F-Droid build of the same source | Not ours; never share our keys with F-Droid or vice versa |
| **Debug key** | Local, disposable | `debug.keystore` for local debug builds only | Irrelevant — regenerate freely |

Play's stated requirement for the upload key is a **Java keystore (`.jks` or
`.keystore`) holding an RSA key of 2048 bits or more**. Google recommends the
upload key and app signing key be different, which is automatic here because
Play generates its own.

Two consequences worth internalising:

- **Play and F-Droid are permanently different signature domains.** The same app
  from the two stores cannot upgrade over one another; users must uninstall to
  switch. This is a deliberate project decision, not a problem to fix.
- New apps are enrolled in Play's **quantum-ready hybrid signing** with
  Google-generated keys, plus a separate classical key for devices older than
  Android 16. Nothing on our side needs to change for that.

## Where to keep the keystore

A dedicated private directory outside this repository — `~/.pageless-release/`
with mode `700` is the convention used here. The properties that matter:

- **Outside the repository**, so no `git add -f` accident is possible, even though
  `.gitignore` covers the file patterns.
- **Encrypted at rest**, ideally by full-disk encryption.
- **Not** inside `~/.android/`. That directory holds `debug.keystore`, and keeping
  the upload key beside the debug key invites exactly the confusion this document
  exists to prevent.
- **Not inside a directory that syncs to the cloud in plaintext** (Nextcloud,
  Dropbox, Drive…). The only copy that should ever leave the machine is one that
  was encrypted first.

Full-disk encryption protects against a stolen machine, not against disk failure —
hence the backup below.

## One-time: generate the upload key

Run this yourself; no agent or CI needs to see it.

**Do not pass `-storepass` or `-keypass` on the command line.** Omitting them makes
`keytool` prompt interactively, which keeps the password out of your shell history
and out of the process list where any local process could read it.

```sh
mkdir -p ~/.pageless-release && chmod 700 ~/.pageless-release

keytool -genkeypair -v \
  -keystore ~/.pageless-release/pageless-upload.jks \
  -alias pageless-upload \
  -keyalg RSA -keysize 4096 \
  -validity 10000 \
  -dname "CN=Pageless, O=Pageless, C=PT"

chmod 600 ~/.pageless-release/pageless-upload.jks
```

**One password, used for both store and key.** Modern `keytool` creates a PKCS12
keystore by default (even with a `.jks` filename), and PKCS12 does not support a
key password that differs from the store password — `keytool` will say so and
ignore the second one. This is fine: AGP reads such a keystore without any
`storeType` declaration, which was verified on this project with a throwaway key
generated by exactly the command above.

- `-keysize 4096` comfortably exceeds Play's 2048-bit minimum.
- `-validity 10000` (~27 years) keeps the key valid far beyond any plausible
  release horizon.
- Use a **non-personal certificate identity**. The DN is embedded in every
  upload; it does not need to be a legal name.
- Keep the keystore **outside this repository**, even though `.gitignore` covers
  `*.jks`, `*.keystore`, `*.p12` and `keystore.properties`.

### Back it up before using it

- The **password** goes in a password manager. One that supports **file
  attachments** (KeePassXC, for instance) can hold the `.jks` in the same entry,
  which is the highest-value backup available: the database is encrypted, so
  syncing it off-machine costs nothing in safety, and the key travels with its
  password. At ~4 KB the keystore is negligible next to a typical database.

  With KeePassXC — in the GUI, open the entry, then **Advanced** tab →
  **Attachments** → **Add**. From the CLI (**close the database in the GUI
  first**, or its next save can clobber the CLI's write and provoke a sync
  conflict):

  ```sh
  keepassxc-cli mkdir "$KDBX" Pageless
  keepassxc-cli add "$KDBX" "Pageless/Play upload key" \
    --username pageless-upload \
    --url https://play.google.com/console \
    --notes "Upload key for live.pageless.mobile. PKCS12; one password for store and key." \
    -p
  keepassxc-cli attachment-import "$KDBX" \
    "Pageless/Play upload key" pageless-upload.jks \
    ~/.pageless-release/pageless-upload.jks
  ```

  `keepassxc-cli show` has no `--attachments` flag (verified against 2.7.12), so
  confirm the attachment landed by round-tripping it:

  ```sh
  keepassxc-cli attachment-export "$KDBX" \
    "Pageless/Play upload key" pageless-upload.jks /tmp/check.jks &&
    cmp /tmp/check.jks ~/.pageless-release/pageless-upload.jks &&
    echo OK && rm /tmp/check.jks
  ```

- At least one **offline** copy, encrypted, on separate media — a synced password
  database shares a failure domain with the cloud account that syncs it:

  ```sh
  gpg -c --cipher-algo AES256 \
    -o /run/media/$USER/<stick>/pageless-upload.jks.gpg \
    ~/.pageless-release/pageless-upload.jks
  ```

- Record what the key is for, its alias, and how to recover it, so a future
  maintainer is not guessing.

### Restoring on another machine

The reverse of the two sections above: extract the attachment back to
`~/.pageless-release/`, `chmod 600` it, and write `keystore.properties` pointing
at it. Before trusting the restored key, confirm with `keytool -list -v` that its
SHA-256 fingerprint matches the one recorded below.

Automating this necessarily hard-codes personal vault paths, so the maintainer
keeps that script in a private dotfiles repository rather than here.

Losing the upload key is recoverable — Google can reset it — but that costs a
support round trip, so treat it as precious anyway.

## Configure the build

Create `keystore.properties` in the repository root. It is git-ignored
(`.gitignore` line 15) and read by `app/build.gradle.kts`:

```properties
storeFile=/home/<you>/.pageless-release/pageless-upload.jks
storePassword=…
keyAlias=pageless-upload
keyPassword=…
```

To write it without the password entering your shell history, let the shell prompt
for it instead of typing it inline:

```sh
cd /path/to/pageless-mobile
read -rs "?Upload keystore password: " KS_PW && printf '\n'
cat > keystore.properties <<EOF
storeFile=$HOME/.pageless-release/pageless-upload.jks
storePassword=$KS_PW
keyAlias=pageless-upload
keyPassword=$KS_PW
EOF
unset KS_PW
chmod 600 keystore.properties
```

(`read -rs "?prompt"` is zsh syntax; in bash use `read -rsp "prompt: " KS_PW`.)
Both password fields get the same value, for the PKCS12 reason above.

Environment variables work too, and take second priority after the file — this
is the hook for eventual CI automation:

```
PAGELESS_UPLOAD_STORE_FILE
PAGELESS_UPLOAD_STORE_PASSWORD
PAGELESS_UPLOAD_KEY_ALIAS
PAGELESS_UPLOAD_KEY_PASSWORD
```

**If no key is configured, release builds stay unsigned.** That is deliberate and
load-bearing: `.github/workflows/release.yml` and F-Droid both run
`assembleRelease` on machines with no upload key, and F-Droid signs with its own
key. Only the Play upload needs signing.

If `keystore.properties` names a store file that does not exist, the build logs a
warning and produces an unsigned artifact rather than failing silently.

## Build the signed bundle

```sh
export JAVA_HOME=/opt/android-studio/jbr
export ANDROID_HOME=~/.Android
./gradlew bundleRelease
```

Output: `app/build/outputs/bundle/release/app-release.aab` — this is what gets
uploaded to Play.

`./gradlew assembleRelease` also becomes signed when a key is configured, and the
filename changes from `app-release-unsigned.apk` to `app-release.apk`. That APK
is useful for local verification and GitHub releases; Play wants the `.aab`.

## Verify before uploading

Confirm the artifact carries the certificate you expect:

```sh
# The AAB: Play verifies the classic JAR signature
jarsigner -verify -verbose:summary app/build/outputs/bundle/release/app-release.aab

# The APK, with certificate details and fingerprints
~/.Android/build-tools/36.0.0/apksigner verify --print-certs \
  app/build/outputs/apk/release/app-release.apk
```

Expect `jar verified.` and a `Signer #1 certificate DN` matching your upload
certificate. Self-signed warnings are normal for an upload key.

Also worth checking on the first upload, per **pm-a6l.11**: package name,
`minSdk`/`targetSdk`, `versionCode`/`versionName`, and that the release network
policy still forbids cleartext.

## Fingerprints: what is safe to record

Certificate **fingerprints are public information** and safe to record in this
repo or an issue — they are how you later confirm an artifact was signed with the
right key:

```sh
keytool -list -v -keystore ~/path/to/private/pageless-upload.jks -alias pageless-upload
```

The upload certificate in use is:

| Field | Value |
| --- | --- |
| Subject | `CN=Pageless, O=Pageless, C=PT` |
| Key | 4096-bit RSA, `SHA384withRSA` |
| Valid until | 2053-12-23 |
| **SHA-256** | `A8:29:4C:87:02:9A:51:0E:1E:5E:E5:D8:01:83:BE:DD:FE:BC:A4:60:D6:51:27:AB:C1:F7:2C:61:00:04:7C:2A` |
| SHA-1 | `54:92:28:B5:73:2E:2F:83:9A:59:12:05:8E:16:3B:CE:B0:6E:FA:1C` |

A restored keystore, or an artifact about to be uploaded, whose fingerprint does
not match the SHA-256 above is signed with the **wrong key** — do not upload it.
Read an artifact's own signer certificate rather than trusting the build:

```sh
unzip -p app/build/outputs/bundle/release/app-release.aab META-INF/PAGELESS.RSA |
  keytool -printcert
```

Never commit the keystore file itself, any password, or the recovery details
that would let someone reconstruct access to it.

## CI signing is deliberately deferred

The first Play upload is manual. Automating signed uploads means putting the
upload key and its passwords into CI secrets, which is a meaningful expansion of
the attack surface for a project whose CI currently holds nothing sensitive. The
environment-variable path above exists so that automation is a configuration
change rather than a rewrite, but it stays off until after the first production
release.
